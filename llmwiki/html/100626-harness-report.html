01 · LLMWIKI LÀ GÌ

Knowledge-base harness cho AI agent

llmwiki là một template deploy được: thả vào project bất kỳ, nó cho agent (Claude Code, OpenCode…) một bộ nhớ wiki có cấu trúc + bộ quy trình làm việc. Triết lý: prompt ra lệnh một lần — context cấp dữ liệu — harness là cả môi trường vận hành.

3 vòng lặp cốt lõi legacy

  • wiki-loop: ingest (file mới trong raw/ → distill thành wiki) · query (tổng hợp trả lời từ wiki) · lint (dọn wiki định kỳ)
  • dev-loop: propose (lập kế hoạch, DỪNG chờ duyệt) · impact-check · safe-change · verify-before-commit
  • orchestrate: orca-workflow (propose → gate → dispatch đa agent) · orca-onboard

6 bất biến (rules) legacy — trước đây chỉ là chữ

  • R1 — agent không bao giờ ghi vào raw/ (inbox của con người)
  • R2 — mọi wiki file phải có ## Origin (truy được nguồn)
  • R3 — index.md luôn khớp tập file wiki
  • R4 — mọi thao tác được ghi log.md
  • R5 — wiki file chỉ nằm trong concepts/ entities/ sources/ draft/
  • R6 — mọi commit phải qua verify (typecheck/lint/smoke)

Vấn đề đã phát hiện → lý do nâng cấp hôm nay

  • 6 rules trên chỉ nằm trong CLAUDE.md — model được dặn chứ không bị buộc; quên là hệ thống lặng lẽ sai
  • log.md do model tự ghi — quên là log thiếu, không ai biết
  • Không có gì đo wiki tốt lên hay xấu đi
  • Kết luận: đã harness ~70% (process + knowledge), thiếu 30%: enforcement + observability + evals

Nguyên tắc giải pháp (đã chốt) hôm nay

  • Mọi thứ chạy ngầm — 0 slash command mới
  • Thứ chạy thường xuyên phải là 0 token (Python/shell local)
  • LLM chỉ xuất hiện ở eval định kỳ tắt được (~$1-5/tuần)
  • Vendor-agnostic: logic nằm ở validators dùng chung; mỗi CLI vendor chỉ là adapter mỏng — có recipe để cook bản mới

03 · KIẾN TRÚC MỚI

5 lớp harness — logic tách khỏi chỗ cắm

Bất biến thiết kế: logic enforcement chỉ sống ở validators/. Adapter của vendor nào cũng mỏng. ~80% hệ thống (L0 + validators + L2 + L4) dùng lại nguyên xi khi đổi vendor. Kéo từng ô để khám phá.

Lớp MỚI (emerald) bảo vệ tài sản LEGACY (indigo)

Contract của validator — trái tim recipe

  • 2 chế độ gọi: stdin JSON (hook realtime) và argv files (pre-commit/CLI)
  • Exit 0 = pass · Exit 2 = vi phạm, lý do trên stderr viết cho agent đọc và tự sửa
  • Fail-open: payload hỏng / không tìm thấy validator → cho qua, L2 vẫn đỡ — harness lỗi không bao giờ brick phiên làm việc
{ "action": "write" | "bash" | "stop",
  "file_path": "wiki/concepts/x.md",
  "content": "...",          // thiếu → đọc disk
  "command": "...",          // action=bash
  "wiki_dir": "path/wiki" }  // action=stop

Cook bản vendor mới — 4 bước (recipe.md)

  • 1. Viết adapter L1: normalize payload vendor → JSON contract → subprocess validator → map exit 2 sang cơ chế block của vendor (<100 dòng)
  • 2. Trỏ L3 vào transcript format của vendor (ccusage hỗ trợ sẵn 15+ CLI)
  • 3. Đổi block providers: trong promptfooconfig
  • 4. L0 + validators + L2 giữ nguyên — copy pre-commit config, sửa prefix path
  • Mức block per vendor: Claude Code đủ 3 tầng · OpenCode tốt · Cursor trung bình · Codex yếu → L2 là gate cứng duy nhất

05 · LUỒNG LÀM VIỆC MIX

Luồng cũ vẫn nguyên — các chốt chặn mới cài vào giữa

Không có bước nào của quy trình cũ bị thay; điểm khác duy nhất là giờ đây sai ở đâu bị chặn bằng máy ngay tại đó. Indigo = bước cũ · Emerald = chốt mới.

① Mỗi tool call trong phiên agent (mọi luồng đều chạy qua đây)
② Dev-loop: propose → gate → implement → commit (luồng cũ + 3 chốt mới)
③ Wiki-loop: tri thức vào hệ thống (luồng cũ) + vòng đo mới chạy nền

Những gì KHÔNG đổi

  • Mọi skill, mọi loop, mọi quy tắc nội dung — y nguyên
  • Propose vẫn dừng chờ duyệt; wiki entry vẫn chỉ tạo sau commit
  • Cách bạn dùng hằng ngày không khác gì — 0 lệnh mới phải nhớ

Những gì đổi về bản chất

  • Rule từ "lời dặn" → "luật vật lý": vi phạm bị chặn ngay tại tool call hoặc tại commit
  • Log từ "model nhớ thì ghi" → "máy luôn ghi"
  • Chất lượng wiki từ "cảm giác" → "số liệu CSV + pass-rate"
